# Подключение Telegram

TelegramModule отправляет украинские сводки с интервалом от последней отправки в БД. После настройки включи TELEGRAM_ENABLED=true в .env и выполни docker compose up -d api. Токен и chat ID обязательны только при включении.

1. В Telegram открой официального [@BotFather](https://t.me/BotFather), отправь `/newbot`, выбери имя и username. Сохрани выданный токен в серверном `/root/aircontrol/backend/.env` как `TELEGRAM_BOT_TOKEN`. Это другой секрет, не DEVICE_TOKEN. В Git/чат его не отправляй.
2. Открой созданного бота и нажми **Start**, либо отправь `/start`. Бот должен получить сообщение от тебя, чтобы мы определили chat ID.
3. На сервере из `/root/aircontrol/backend` выполни:

```sh
docker compose run --rm --no-deps api npm run telegram:chat
```

Команда читает свежую .env через Compose и выводит ID, тип и название/username чатов. Выбери свой личный чат, запиши его ID в `.env` как `TELEGRAM_CHAT_ID`. Если список пуст, отправь боту новое сообщение и повтори. Для нового бота webhook не нужен; у уже используемого бота getUpdates может конфликтовать с webhook/другим polling-процессом — не отключай их вслепую.

4. Включи TELEGRAM_ENABLED=true и пересоздай API. Проверяй доставку реальной сводки в канале и статус в telegram_deliveries.

Следующие расширения: сводка за день, длительное превышение и восстановление. Моковые показания должны явно оставаться тестовыми. Сводки уже обрабатываются отдельным worker со статусами в БД; сбой Telegram не блокирует сохранение измерений.

Источники: [официальный tutorial](https://core.telegram.org/bots/tutorial), [getUpdates](https://core.telegram.org/bots/api#getupdates), [sendMessage](https://core.telegram.org/bots/api#sendmessage).

## Канал

Добавь бота администратором канала с правом публикации сообщений. Отправь новый пост после добавления и выполни telegram:chat: выбери запись type=channel. Сохрани числовой ID (обычно отрицательный) в TELEGRAM_CHAT_ID. Не выбирай ID личного диалога, если цель — канал. При получении обновлений helper также показывает title/username для различения чатов. Токен не выводится.

## Сводки

Раз в 10 секунд и при старте API проверяется последняя запись telegram_deliveries для device/chat. После успешной отправки следующий отчёт разрешён через TELEGRAM_REPORT_INTERVAL_MINUTES от sent_at (по умолчанию 60). После ошибки/незавершённой попытки интервал отсчитывается от attempted_at. Без истории первая сводка отправляется сразу. После долгого простоя отправляется один свежий отчёт, без рассылки пропущенных периодов.

Данные берутся за [now - TELEGRAM_REPORT_WINDOW_MINUTES, now), по умолчанию последний час. Это скользящий период, без привязки к :00/:15 и без прежней минуты grace. Интервал отправки и глубина данных задаются отдельно в .env, целыми минутами от 1 до 44640; Compose передаёт их API. Например, 1440/1440 — сутки между отправками и данные за последние 24 часа, а не фиксированное время или календарный день. Календарный месячный отчёт — отдельная будущая задача; исходные measurements остаются основой аналитики.

Время отображается в Europe/Kyiv, обе даты начала/конца включены в текст. Местоположение: Кривий Ріг · Центрально-Міський район, Гданцівка. Статистика по measured_at для DEVICE_ID; mock/pms5003 раздельно. Null-время считается отдельно и не включается в статистику. Поздние данные не меняют отправленный текст. Скользящие периоды не гарантируют полного неперекрывающегося покрытия истории.

360 фактов на украинском находятся в src/modules/telegram/data/air-facts.uk.json. У каждого ID и sourceUrl (EPA, NOAA/NWS, NASA, USGS, Met Office), ссылка включена в сообщение. Выбор случайный, последние 10 выбранных фактов исключены. Полный цикл из 360 дней без повторов пока не реализован; текущая тестовая рассылка — раз в час. Это общие факты, не объяснение причин текущих значений и не прогноз погоды. Дата редакционной проверки источников: 2026-09-08. Свежих метеоданных и AI-генерации нет.

Структура: MeasurementsService.findForPeriod получает entity за [start, end); calculateStatistics в measurements/utils считает среднее, минимум и максимум каждого PM-поля отдельно для каждого source. TelegramService собирает эти шаги, summary.ts формирует текст, TelegramClient отправляет HTTP-запрос. Для небольшого потока одного устройства загружаем измерения в память; при росте количества устройств/длительности окна стоит вернуть SQL AVG.

TelegramDeliveriesService работает через Repository с существующей таблицей. Миграция добавляет window_start, attempted_at, schedule_key; исторические строки сохранены, начало старого окна восстановлено как window_end минус 15 минут. Перед отправкой вставляется sending, после успеха — sent/sent_at/message_id, при ошибке — unknown. Уникальный schedule_key на основе предыдущего отчёта не позволяет конкурентным проверкам отправить два следующих отчёта, даже если у них отличается now. Дополнительно сохранена уникальность device/chat/window_end.

При sending/unknown проверь канал вручную. Тот же отчёт автоматически не повторяется, новая попытка свежего отчёта допускается после интервала. Возможен пропуск: exactly-once не обещаем. Старые pending/failed также учитываются по attempted_at, но не возобновляются. Поля старой очереди остаются в схеме для совместимости; очереди retry нет. Только ошибки логируются, секреты скрыты.

Рассылка работает независимо от сохранения измерений. Для остановки задай TELEGRAM_ENABLED=false и выполни docker compose up -d api.

Для тестирования установлены INTERVAL/WINDOW = 60/60. Для отчёта раз в сутки за последние сутки задай обе TELEGRAM_REPORT_*_MINUTES=1440 и пересоздай api. Среднее арифметическое считается по сохранённым снимкам, не по всем UART-кадрам. Время минимума/максимума — measured_at; при одинаковом значении указывается самое раннее время. Короткие пики между сохранёнными снимками могут не попасть в отчёт.

Оформление: Telegram HTML (жирные заголовки/числа, отдельные строки среднего и экстремумов, краткое сравнение размеров с условной волосиной 70 мкм). Текст факта и ссылка экранируются. Технические пояснения о локальности/снимках остаются в документации, из поста удалены. Часовой интервал сохранён; оценка нормы/рисков отложена до отдельного согласования суточного отчёта.
